### Задание 1

1.1. Состав бюджетных и финансовых показателей, как правило, четко структурирован и стандартизован в пределах одной компании, 
представляя собой набор взаимосвязанных таблиц. Для решения задачи хранения и обработки таких данных хорошо подходит 
СУБД реляционного типа. Они гарантируют целостность и чёткую структуру данных. Примеры СУБД: PostgreSQL, Oracle Database, 
Microsoft SQL Server.

1.1.* Ответ в контексте ответа на предыдущий вопрос. СУБД реляционного типа имеют встроенные функции вычисления хеша данных. 
Если хеширование (т.е. процесс создания хеша данных) в СУБД стало занимать длительное время, то при условиях исчерпания 
возможностей оптимизации встроенных механизмов СУБД и невозможности расширения аппаратных ресурсов и оптимизации ОС можно 
рассмотреть вызовов API к высокоскоростным хранилищам, например, Redis.

1.2. Для архитектуры с множеством лендингов и единой CRM оптимально использовать комбинацию реляционной (SQL) и 
документоориентированной (NoSQL) СУБД, чтобы обеспечить высокую скорость, гибкость и надежность хранения данных.
Для СУБД лендингов и лидов важна максимальная скорость записи и отказоустойчивость при кратковременных пиках трафика, 
поэтому целесообразно применение СУБД типа NoSQL (документоориентированная) или легкая реляционная СУБД. 
Примеры СУБД: MongoDB или Redis (для кэширования временных сессий и сохранения потока заявок до отправки в CRM).

Для CRM важны надежность, сложные транзакции, связи между данными и аналитика, поэтому здесь лучше рассмотреть СУБД 
реляционного типа. Примеры СУБД: PostgreSQL или MySQL.

1.3. Как СУБД, сформированной согласно структуре компании, лучше рассмотреть СУБД типа NoSQL с иерархической моделью 
данных. Они оптимизированы для организации данных в древовидной структуре. Примеры СУБД: MongoDB.

1.4. Для быстрого формирования маршрутов больше подходит СУБД типа NoSQL со структурой графов для семантических запросов. 
В ней данные хранятся в виде узлов, ребер и свойств. Примеры СУБД: Neo4.

### Задание 3

3.1. Реляционные СУБД превосходят нереляционные по:
1. строгому стандарту обработки транзакций;
2. высокой гибкости при аналитике сложных взаимосвязей;
3. развитой нормализации данных;
4. проверенной надежности и единому стандарту языка;
5. наличию и понятности схем хранения данных.

3.1.* Системы NewSQL представляют собой «золотую середину», объединяя масштабируемость и распределенную архитектуру NoSQL 
с надежностью транзакций и удобным SQL-интерфейсом традиционных SQL-баз. Они позволяют приложениям расти без горизонтальных 
ограничений, не жертвуя целостностью данных. Главные преимущества NewSQL перед предшественниками можно разделить на три 
основные категории.

Преимущества перед классическими SQL-базами:
- Неограниченная горизонтальная масштабируемость: Классические SQL-базы (такие как MySQL или PostgreSQL) обычно ограничены 
мощностью одного сервера. NewSQL разбивают (шардируют) и распределяют данные по десяткам или сотням узлов автоматически, 
справляясь с огромными нагрузками. 
- Отказоустойчивость и высокая доступность: Благодаря встроенной географической репликации узлов, сбой одного или нескольких 
серверов не приводит к простою системы или потере данных.

Преимущества перед NoSQL:
- Поддержка ACID-транзакций: В отличие от многих NoSQL решений, жертвующих свойствами ACID ради скорости, NewSQL гарантируют 
абсолютную согласованность и целостность данных. Это критически важно для финансовых, банковских или e-commerce проектов.
- Привычный SQL и реляционная модель: Разработчикам не нужно изучать специфические API или отказываться от сложных запросов 
и связей (JOIN), к которым они привыкли в реляционных базах. Поддержка стандарта SQL делает переход более простым.
Примеры СУБД: Google Cloud Spanner, CockroachDB, YugabyteDB, TiDB.

### Задание 4

В случае наличия большого количества машин, выделенных для работы с СУБД, следует выбирать тип СУБД по критериям качественной 
реализации распределенных вычислений и масштабирования.
Очевидно, что при возрастании количества машин растет риск их отказа. Он коррелирует со свойством устойчивости к 
разделению (partition tolerance). Поэтому при заданных входных условиях здесь справится лучше модель распределённых 
вычислений класса AP, которая не гарантируется целостность, но при этом выполняет условия доступности и устойчивости к 
распаду на секции. Однако, указанный выбор модели может измениться при появлении требований конкретной бизнес-задачи.
